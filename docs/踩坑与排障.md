# 搭建踩坑与排障

以下分为“搭建记录中实际遇到的问题”和“源码明确防范的边界”。证据来自现有维护文档、搭建会话记录、源码及测试；未写成实际发生的错误，不应当作已经发生过。整理日期：2026-10-29。

## 1. 误用参考项目的部署入口

**症状：** 按旧 README 设置了 Claude URL 密钥或运行 `setup:google`，却没有个人归档、周包或 ChatGPT 即时查询。

**原因：** 仓库沿用了参考项目的 Provider 和工具目录，但本方案新增的入口是 `src/workflow/worker.ts`，部署配置是 `wrangler.workflow.toml`。旧文档描述的是 `src/index.ts` 路径。

**处理：** 从当前 README 的复现流程开始，使用 `workflow:setup`、`npm run deploy` 和 `/live-mcp`。旧脚本仅保留作参考，旧授权脚本可能打印令牌，不用于本方案。

**验证：** 检查模板 `main`，确认部署产物入口；当前 MCP 应仅暴露 `fetch_latest_health` 和 `health_packet`。参考说明不能作为当前线上状态证明。

**证据：** `package.json`、`wrangler.workflow.toml.example`、`src/workflow/mcp.ts`。这是混合文档造成的复现风险，不代表曾发生实际数据泄露。

## 2. 新 Cloudflare 账户还没有 workers.dev 子域名

**症状：** 初始化已创建部分资源，第一次部署中断或提示创建子域名。

**原因：** 自动资源创建不代表账户的 Worker 公网地址已经就绪。初始化也不是原子事务，前面创建的 KV/D1 可能已存在。

**处理：** 先检查 Cloudflare 控制台和已生成的配置，不反复运行 `provision` 建同名资源。若配置已齐全，执行 `pnpm exec wrangler deploy -c wrangler.workflow.toml`，按终端提示完成子域名；再执行 `npm run workflow:setup -- init-access` 和 `npm run workflow:setup -- init-mcp` 补装本地保存的访问密钥。

**验证：** 本人部署地址 `/health` 为 200；`secrets/` 中保存三个独立密钥；未授权 `/export` 为 401，授权后 `/status` 可读。

**证据：** 原维护记录明确记载了首次部署恢复方式；`initializeAccess` 保留本地已有令牌。当前完整实例需要 3 个 KV：`TOKENS`、`CACHE`、`OAUTH_KV`，另加 1 个 D1。

## 3. 本机无法直连 workers.dev

**症状：** 浏览器或维护脚本连 Worker 超时，但 Cloudflare 显示部署成功。

**原因：** 搭建机器的直连路径未成功；这是该网络环境的观测，不能推广为所有地区或所有网络都无法访问。

**处理：** `scripts/health.ps1` 可沿用 Windows 已开启的简单系统代理，或显式传 `-Proxy http://127.0.0.1:端口`。先确认代理本身可用，不随意修改系统网络。此参数只影响该维护脚本；不能假设 Node、Wrangler 和浏览器自动使用同样的代理配置。

**验证：** 用同一路径请求 `/health` 和有权限的 `/status`。先区分网络超时与 HTTP 401/403，后者说明请求已经到达服务。

**证据：** 原维护记录记载线上验收通过既有系统代理；`health.ps1` 明确实现代理读取和参数。

## 4. OAuth 页提交后出现 `Invalid origin`

**症状：** 已进入健康数据连接页，填写正确连接密钥后返回 `Invalid origin`。

**原因：** 早期授权页的 `Referrer-Policy: no-referrer` 与严格 Origin 检查冲突：浏览器 HTML 表单 POST 可能携带 `Origin: null`。此外，新实例若未将 `PUBLIC_ORIGIN` 替换为自己的域名，请求实际来源与配置不同，也会被拒绝。

**修复：** 授权页采用 `Referrer-Policy: same-origin`，保留严格同源校验；部署者在 `wrangler.workflow.toml` 的 `[vars]` 把 `PUBLIC_ORIGIN` 填为自己的 Worker HTTPS origin，再运行 `npm run deploy`。资源元数据会使用同一配置。该值只含协议、域名及必要端口，不含路径、查询、片段或凭据。不要通过取消来源校验解决。

**验证：** 从 ChatGPT 新发起连接，确认表单提交通过、返回 ChatGPT 并成功换取授权；错误来源应仍返回 403。若显示配置提示并返回 503，先检查 `PUBLIC_ORIGIN` 是否缺失或非法。旧页面不会因后台部署而自动更新，需重新开始。

**证据与状态：** `src/workflow/oauth.ts` 的响应头和来源判断。既有 2026-10-29 记录称已在隔离 Edge 中验证浏览器表单；本次文档整理未重新执行线上授权。

## 5. 正确批准后又提示“不是在这个浏览器开始授权”

**症状：** 授权批准后没有正确跳回 ChatGPT；重提旧表单出现 `This authorization was not started in this browser`。

**原因：** 既有排障记录将该次故障定位为 CSP 阻止表单批准后的 ChatGPT 回跳；授权 handle 已消耗，继续重提旧表单会失效。这条报错也可能由真正丢失浏览器 Cookie 导致，不能一律视为 CSP。

**修复：** 授权页 CSP 允许 `form-action 'self' https://chatgpt.com`，保留浏览器绑定 Cookie 与 PKCE。关闭旧页，在同一浏览器会话从 ChatGPT 重新发起；不需要因此更换 Google 令牌或连接密钥。

**验证：** 同一浏览器内完成授权页 → POST → ChatGPT 回调 → 授权码交换；没有 Cookie 的请求继续拒绝。错误连接密钥才计入失败次数，不让其他流程错误消耗密钥重试预算。

**证据与状态：** `src/workflow/oauth.ts`，既有真实 Edge 验证记录。单独用 HTTP 客户端取到 302 不足以证明浏览器 CSP/Cookie 流程完整。

## 6. 一开始可读，过几天全部鉴权失败

**症状：** 起初同步正常，之后多个数据流持续 `error`，重新授权暂时恢复。

**可能原因：** refresh token 失效、权限被撤销、OAuth 客户端错误或测试发布模式限制。Google 的 External 应用在 Testing 状态下，部分范围的刷新令牌存在 7 天限制；切换 Production 本身不等于完成所有审核。

**处理：** 先看 Google 控制台发布状态、授权范围和令牌安装；按实际官方要求处理发布/验证后，用当前 `authorize health` 或 `authorize gmail` 重新授权。不要在聊天、issue、日志中贴令牌。未获得新 refresh token 时不要覆盖可用旧值。

**验证：** 不只确认首次 access token 能用，还应在其过期后验证后台刷新与再次读取成功。`/health` 始终 200 不能证明 Google 授权正常。

**证据与状态：** `src/providers/google/oauth.ts` 实现到期前刷新、保留旧刷新令牌；原维护记录称后台刷新已验证。Testing 限制应查[Google 令牌有效期说明](https://developers.google.com/identity/protocols/oauth2#expiration)。这是运维风险提示，并非断言原实例曾发生 7 天后失效。

## 7. 按“通用筛选格式”读 API 报 400，或只拿到第一页

**症状：** 某类 reconcile 请求返回 400；或历史看起来少很多，但请求状态为成功。

**原因：** Google Health v4 的筛选字段随数据类型变化，不能把一条 filter 复制到所有接口。旧 reconcile 实现只取单页，也存在静默截断风险。

**修复：** 基础 `reconcile.ts` 对已知易错来源省略 filter，逐页取回后按 civil date 缩小范围；新增明细接口在 `extra.ts` 按 sample/interval/daily 类型生成已匹配的 filter。所有这些有分页的读取均处理 `nextPageToken`，检测重复 token，并设置 20 页预算。

**验证：** 本地测试覆盖多页、重复 token、超预算；手动回补不超过 7 天一批。达到预算必须明确失败，不能把已取的前 20 页当完整数据。不要把本段简化成“Google 全部接口都不支持 filter”。

**证据：** `src/providers/google/reconcile.ts`、`extra.ts`、`test/workflow/workflow.test.ts`、`test/providers/google/extra.test.ts`。400 观察写在参考实现注释中；分页截断是本方案已经修正的代码风险。

## 8. 空数据被算成零、没有分期被算成没睡

**症状：** 初始历史不足却有“28 天基线”；某天显示 0 小时睡眠或 0 步；源端没有 VO₂ max 却被当作数值异常。

**原因：** 无记录、读取失败和真实零值的含义不同。睡眠映射在无分期时可能产生零分钟，但不表示整晚未睡。部署初期可用天数也不足以支持完整基线。

**修复：** 每流状态单独保存；失败不覆盖上次成功观测；空数据保留空数组；统计只用有效值并报告有效天数。缺睡眠分期时不把 `minutesAsleep: 0` 纳入均值；不把每段睡眠强制标为主睡眠。数据包附带解释规则。

**验证：** 查看 `latestAttempts`、观测的 `fetched_at`、`validDays`、`expectedDays`。多个 VO₂ max 来源成功为空可以是正常情况。没有记录时问手机是否同步、设备是否生成，而不是自行补零。

**证据与状态：** `core.ts` 的 `collect/statistics` 及相应测试。既有真实读取记录确认 VO₂ max 三来源成功为空；本次没有附带个人数值。

## 9. 温度、血氧、运动分钟的名字误导解释

**症状：** 把皮肤温度当核心体温；把每日血氧区间边界说成最低/最高读数；把加权活动分钟当成真实运动时长。

**原因：** 适配层沿用了部分 Fitbit 风格类型，但 Google 字段语义并不完全相同。

**修复：** 夜间温度用 `nightlyTemperatureCelsius - baselineTemperatureCelsius` 得到相对变化；血氧显式保留 `lowerBoundPercentage/upperBoundPercentage`，按置信边界解释，旧存档 `min/max` 同理；活动区间分钟与真实运动分钟分别说明。源端字符串 `NaN` 不转为有效数值。

**验证：** 看实际字段名、单位和来源，不只看图表标签。温度映射与血氧字段名有单元测试；活动区间原始汇总保留，不捏造训练负荷或恢复分数。

**证据：** `src/providers/google/metrics.ts`、`test/providers/google/metrics.test.ts`、`core.ts` 分析约束。这是字段映射已纠正的语义问题，不是医疗结论。

## 10. 新增设备最后同步时间后 403

**症状：** 大多数健康流正常，设备状态单项失败。

**原因：** 设备配置需要单独的 `googlehealth.settings.readonly`。已有活动、健康指标和睡眠权限不会自动包含它。

**处理：** 默认不读设备状态。确有需要时，在 Google 控制台添加对应只读范围，运行 `npm run workflow:setup -- authorize health-device oauth-client-health.json`，确认返回范围齐全，再设置 `DEVICE_STATUS_ENABLED = "true"` 并重新部署。

**验证：** 验证设备状态流及其返回时间；该时间只是设备同步线索，不代表每项健康数据都完整。不要只改开关而不重新授权。

**证据与状态：** `workflow-setup.ts`、`core.ts`、包内限制说明；源码注释记录过早期探测设备范围。原搭建默认未启用此额外权限。

## 11. Gmail 超时后不知道究竟发没发

**症状：** `/status` 中周包为 `needs_review` 或长期 `sending`；再次触发显示 `already_reserved`。

**原因：** 网络失败可能发生在 Gmail 已接受邮件之后。若一超时就自动重发，可能产生重复邮件。

**设计与处理：** 先写入唯一周标识 `sending`，再调用 Gmail；确认成功写 `sent`，异常写 `needs_review`。系统不自动重发状态不明的周。先查看本人已发送邮件和收件箱，再决定人工处理；临时可用 JSON 导出。

**验证：** 默认 `WEEKLY_EMAIL = "false"` 时不发信；开启后同一周只保留一次发送预约。真实 Gmail API 成功只证明 API 接受，仍需本人确认收件。不要为了“验收”反复触发真实发信。

**证据与状态：** `src/workflow/gmail.ts` 和去重/异常测试；原记录记载真实 Gmail API 发送成功，不能扩写为长期周邮件已持续验证。

## 12. “可读的后台”被误认为“手机已可日常用”

**症状：** 后台测试通过，手机聊天仍没有工具；或模型直接根据旧聊天/Gmail 周包回答，声称已读取最新健康。

**原因：** 服务端 OAuth 能运行，不代表当前 ChatGPT 账户有自定义 MCP 入口、工具已安装、聊天已启用，或手机端支持相同操作。项目指令也不能创建工具连接。

**处理：** 在实际可用界面完成一次 OAuth、安装并启用工具，首次明确要求调用 `fetch_latest_health`；用手机同账户再次验证。没有入口时先使用本人 JSON 导出，不声称已连接。模型必须检查 `refreshSucceeded`、数据日期和采集状态；失败或 busy 时明确标记归档回退。

**验证：** 看真实工具调用记录，而不仅看回答中“已读取”几个字。回答应含读取时间、数据截至日期；原本未上传的新记录不能被“即时查询”强制取得。

**证据与状态：** MCP 工具说明、项目指令和日常使用文档。服务端链路既有验证与实际账户/手机端体验应分别记录。

## 发布前的快速核对

1. 本机实际 OAuth JSON、`secrets/`、`exports/`、`.dev.vars`、真实 Wrangler 配置均不进入待提交清单；另检查 Git 历史，不能只看 `.gitignore`。
2. 新实例 `PUBLIC_ORIGIN`、ChatGPT MCP 地址与资源声明指向自己的同一公网来源；Google 授权脚本回调另为 `http://127.0.0.1:8787/oauth/callback`，不要混用。示例不沿用任何人的真实部署地址或资源 ID。
3. 按当前锁文件安装并通过本地类型检查、测试与 dry-run；把模拟测试与真实账户验收分开记。
4. 文档写明所需账户/API/设备权限，缺失状态、时区、历史基线和人工验收边界；保留 MIT 上游归属。

这些核对用于保证公开方案可复现，不要求公开个人健康数据、收件截图或密钥作为证据。
